Dhaga Workbench Architecture

One web app, one backend and one database. The browser only ever talks to the backend. The backend is the only part that holds the keys to the database and to Claude.

How a request travels

An agent clicks "Analyse" on a ticket

  1. Browser sends POST /api/cx/tickets/TKT…/analyze
  2. Ticket, customer and order are read from Postgres code
  3. Haiku works out what the customer wants AI
  4. Code works out the facts and applies the rules code
  5. Opus writes the reply from the facts and the policy AI
  6. Code checks every date and amount; Haiku reviews the reply AI
  7. The run is saved to ai_interactions; the browser shows the draft
  8. The agent approves; the ticket status updates in Postgres

The category team clicks "Classify with AI"

  1. Browser sends POST /api/returns/classify
  2. Returns are read from Postgres and cleaned code
  3. Haiku reads each "Other" comment, 8 at a time AI
  4. Reasons are saved on the returns rows
  5. Unsure ones appear in the review queue
  6. A person accepts or corrects; that answer always wins
  7. Charts and flagged products refresh with the new reasons code

When something fails

If this failsWhat the user sees
OpenRouter is down or out of creditCX switches to standard template replies, with a "Fallback mode" banner. Returns classify shows an error and changes nothing.
Claude returns something invalidThe ticket goes to a person with the reason shown on screen
Supabase is unreachableThe status bar turns red; screens show "Couldn't load this" with a Retry button
A table is missingA "Setup needed" warning names the SQL file to run
No keys at all (a fresh clone)The app runs on built-in demo data with template replies
