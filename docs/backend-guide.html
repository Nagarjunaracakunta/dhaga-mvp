Dhaga & Co. MVP · Backend guide

Dhaga Returns Backend

How the returns-insights pipeline turns raw order and return CSVs into return rates and a short list of products, sizes and colours worth investigating.

Stage 1: rules only, no AIPython 3.11 · pandas · FastAPIBranch feat/base-backed-wismo-mvp

Overview

Dhaga sells ethnic wear online. Customers pick a return reason from a dropdown, and many pick "Other" and type a comment, often in Hinglish ("shoulders pe bahut tight hai"). The business question is: which products, sizes or colours are being returned unusually often, and why?

The backend answers that in two stages:

  • Stage 1 (this code): clean the data, compute return rates, and use fixed rules to flag segments that stand out. Every step is deterministic. No language model is called.
  • Stage 2 (not built yet): a language model reads the "Other" comments and classifies them. Stage 1 already marks those rows with needs_llm = True and collects sample comments for each flagged segment.

The design rule, from backend/insights.py: code decides what is notable; a later LLM only explains it. The model will never decide which products to flag.

Run it locally

The project uses a virtual environment in .venv/ built on Python 3.11, which matches the Docker image.

python3.11 -m venv .venv               # first time only
source .venv/bin/activate
pip install -r requirements.txt

python scripts/generate_demo_data.py   # optional: rebuild data/*.csv (seeded, same output every time)
python -m backend.pipeline             # print the report and write data/processed/*.csv
pytest -q                              # 7 tests
uvicorn backend.main:app --reload      # API at http://127.0.0.1:8000, docs at /docs

How data flows

Everything runs through run_pipeline() in backend/pipeline.py. Rows are never silently dropped. Each step returns the rows it kept plus a table of rejected rows with a reason, and those tables are combined at the end.

Two ordering details matter:

  • Returns are validated against the cleaned orders. If an order was rejected, its returns are rejected too, as order_not_found.
  • After cleaning, product name and category on returns are replaced with values from products.csv. The catalogue is the single source of truth for those fields.

The result is a PipelineResult holding products, orders, returns, rejected, summary and candidate_insights.

Validation rules

Checks run in the order below. A row is rejected for the first check it fails, so each rejected row has exactly one reason.

Orders

duplicate_order_idThe order_id appeared earlier in the file. The first copy is kept.
unknown_product_idThe product is not in products.csv
invalid_order_dateThe date is not YYYY-MM-DD
unknown_sizeThe size text is not in the size map (checked during normalization)

Returns

Normalization

All matching ignores case and extra spaces. The maps live in backend/config.py, so supporting a new spelling means adding one entry there.

Size

"medium", " m " and "M" all become M. "Free size", "one size" and "os" become FREE. Anything else is rejected as unknown_size.

Colour

Shades and Hindi names are folded into 10 base colours, for example gulabi, pinkish and baby pink become Pink, and neela and navy become Blue. An unrecognised colour becomes UNKNOWN. It is not rejected, because colour is not required.

Insight rules

find_candidate_insights looks at three levels: whole product, product + size and product + colour. For each one it computes:

return_rate = returns ÷ orders
baseline    = all returns ÷ all orders (12.44% today)
lift        = return_rate ÷ baseline

A segment is flagged only if it passes every rule that applies to it:

RuleThresholdApplies toWhy
Enough returns≥ 15AllAvoids flagging tiny samples
Lift over shop baseline≥ 1.5×AllMust be clearly worse than the shop average
Lift over its own product≥ 1.4×Size and colour onlyStops a bad product from flagging every one of its sizes

Worked example: Floral Midi Dress, size L

48 returns ÷ 115 orders = 41.7%
lift = 41.7% ÷ 12.44% = 3.35×   (passes 1.5×)
product rate = 19.3%; 19.3% × 1.4 = 27.0%   (41.7% passes)
48 returns   (passes 15)

Each flagged segment comes back with its counts, rate, lift, a breakdown by primary_reason, the share still UNCLASSIFIED, and up to 5 sample "Other" comments. Results are sorted by lift, highest first. The insight_id takes the form product_size:SKU4421|L.

All three problems planted in the demo data are found. The Chikankari Top size S flag was not planted. Its known reasons are mostly COLOUR (10 of 14), so it is probably the Mustard colour problem showing up again through one size, not a separate fit issue. This is the kind of overlap a reviewer, or stage 2, should check before acting on it.

For the Floral Midi Dress M and L flags, the dropdown alone points to FIT, but 42% to 61% of those returns are still UNCLASSIFIED. The detail that it is the shoulders only appears in the comments, so stage 2 is needed to confirm it.

Rejected rows

The 10 rejections match the broken rows planted by the generator: 1 duplicate order, and on returns 1 duplicate, 2 bad dates, 1 missing product, 1 unknown product, 1 missing order, 1 product mismatch, 1 unknown size and 1 unknown reason.

Tests

tests/test_pipeline.py has 7 tests, all passing:

  • Size, colour and dropdown-reason mapping.
  • "Other" with and without a comment gets the right needs_llm and classification_source.
  • Validation catches a bad date and a missing product_id.
  • Return-rate arithmetic on a small example.
  • An end-to-end run finds the Floral Midi Dress L and Chikankari Mustard patterns, rejects at least 9 rows, and leaves no duplicate return IDs.

The end-to-end test does not check the Anarkali Suit quality pattern, even though the pipeline finds it.
