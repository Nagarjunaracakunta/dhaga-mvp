# Build Note: CX Copilot

**What it does:** an agent opens a support ticket. Copilot works out what the customer wants, looks up their order, applies Dhaga's rules, and drafts a reply that cites only real order facts and the matching policy. The agent approves, edits or rejects it. Nothing reaches a customer without an agent.

Live: https://nagarjuna2026-dhaga-mvp.hf.space · Data: Supabase (1,800 tickets, 2,500 orders) · Models: Claude via OpenRouter

**Tickets** are synthetic but varied: 1,800 distinct messages in English and Hinglish, with typos, order numbers in the text and mixed tones, generated by `scripts/generate_cx_tickets.py`. The intent mix follows the brief's 58% "where is my order".

## Code vs model

| # | Step | Code or model | Model / temperature | Why |
|---|---|---|---|---|
| 1 | Load ticket, customer, linked order | Code | – | Lookup |
| 2 | Classify intent, pull out order number, detect language | **Model** | Claude Haiku 4.5, **temperature 0** | Hinglish free text ("Kab tak delivery hoga?") is a language problem. Temperature 0 so the same ticket always gets the same label. |
| 3 | Pick the order: number in message → linked order → latest order; check the customer owns it | Code | – | Lookup and comparison |
| 4 | Order facts: days late, cancellable, days since delivery, inside 7-day return window | Code | – | Date arithmetic. A model must never calculate a delivery date. |
| 5 | Rules: confidence below 0.70, unclear intent, RTO, "delivered but not received", damaged or wrong item, someone else's order → hand to a person | Code | – | Business policy has to be predictable and auditable |
| 6 | Choose the policy document for the intent | Code | – | Lookup |
| 7 | Draft the customer reply | **Model** | Claude Opus 5.5, **default temperature, reasoning effort "low"** | Customer-facing writing in the customer's own language. Opus 5.5 does not accept a temperature setting, so we control it with effort and with the checks in steps 8–9. |
| 8 | Fact check: every date, amount, order number and tracking number in the draft must match the order | Code | – | Comparison. Catches invented facts without spending on a model. |
| 9 | Judgement check: answers the question, follows policy, polite, right language | **Model** | Claude Haiku 4.5, **temperature 0** | A yes/no review is judgement, but cheap and repeatable |
| 10 | Failed check → redraft once with the issues listed; fails again → hand to a person | Code | – | Control flow |
| 11 | Log the run (models, prompt versions, cost, time) to `ai_interactions` | Code | – | Audit trail and metrics |
| 12 | Approve / edit / reject / escalate | **Human** | – | The brief requires a deliberate review step for anything customer-facing |

**Two models, why this split:** Haiku runs on every ticket (classify and check) because it's about 4× cheaper and gives a fast yes/no. Opus only writes the reply, where quality is what the customer sees. Tickets the rules send to a person never reach Opus: measured cost $0.00095 instead of $0.0104.

**When validation fails:** every model call must return JSON that matches a Pydantic schema. If the answer is invalid, cut off or refused, the ticket becomes `NEEDS_HUMAN` with the reason on screen. If OpenRouter is down or out of credit, Copilot switches to keyword matching and the agents' existing template replies, and shows a "Fallback mode" banner.

## Patterns and what breaks without each

- **Routing** (steps 2, 5, 6). The intent decides which facts, rules and policy apply. *Without it:* one prompt carries every policy, so it's longer and dearer, the model can apply cancellation rules to a refund question, and risky cases (return-to-origin, lost parcels) get an automatic draft instead of going to a person.
- **Prompt chaining** (classify → draft → check). A cheap step gates the expensive one. *Without it:* every ticket pays for Opus, including the ones a person must handle anyway. In our 5-ticket run, 2 of 5 stopped after the first step.
- **Evaluator-optimizer** (steps 8–10). *Without it:* a draft with a wrong date or amount reaches the agent, and the agent becomes the only check. The test `test_invented_date_triggers_one_redraft` plants a wrong date, which is caught and fixed on the redraft.

## Cost line

Measured on 5 real Supabase tickets through OpenRouter, 3 October 2026:

| Step | Avg tokens (in / out) | Avg cost | Avg time |
|---|---|---|---|
| Classify (Haiku 4.5) | 790 / 32 | $0.00095 | 1.7 s |
| Draft (Opus 5.5) | 1,246 / 177 | $0.00853 | 6.8 s |
| Check (Haiku 4.5) | 849 / 13 | $0.00091 | 1.6 s |
| **Ticket with a draft** | | **$0.0104** | **≈10 s** |
| Ticket sent to a person | | $0.00095 | ≈2 s |

**At Dhaga's volume** (9,000 tickets a week, from the brief), as an upper bound with every ticket drafted:

> 9,000 × $0.0104 = **$93.60 a week** ≈ **₹8,050 a week** ≈ **₹0.89 per ticket** ≈ ₹4.2 lakh a year
> (₹86 per $ is our assumption, not from the brief)

A redraft adds about $0.0094 for that ticket. 82% of the cost is the Opus draft. Writing replies with Sonnet 5.5 instead would cost roughly $0.006 per ticket, but we estimated that rather than measuring it. We don't know an agent's cost per hour; that's a number we'd ask Dhaga for before claiming savings.

## How accurate it is

`python evals/intent_eval.py` scores the classifier against the correct intent for every generated ticket (`data/cx_eval/tickets_labelled.csv`).

| Classifier | Tickets | Correct intent | Unsafe misses* | Cost |
|---|---|---|---|---|
| Claude Haiku 4.5 (prompt `classify_v2`) | 70 (10 per intent) | **70 / 70** | **0** | $0.077 |
| Keyword fallback (no model) | all 1,800 | 72.7% | 99 | free |

\*An unsafe miss is a ticket that needs a person (lost parcel, damage, unclear) given an intent that leads to an automatic draft.

**Read this carefully.** The tickets come from templates, so they are easier than real customer text. 0 errors in 70 means the true error rate is probably below about 4%, not that it is zero. Before go-live we would score 200 real Freshdesk tickets labelled by Arpita's team. The keyword baseline shows why a model earns its place here: rules alone would auto-draft 99 tickets that needed a person.

## What broke that we did not expect

1. **The deploy was green, but the app was down.** The GitHub Action that syncs to Hugging Face passed every time, yet the Space sat in `CONFIG_ERROR`: the Space reads its settings (SDK, port) from a header in `README.md`, and ours had none. We only found it by checking the Space's status, not the pipeline. *Lesson: check the live URL, not the build log.*
2. **The real database didn't match the design.**
   - **Statuses:** tickets use `OPEN / IN_PROGRESS / CLOSED`, not the statuses we designed for. We map between them now.
   - **Missing tables:** two tables we expected didn't exist. A missing logging table broke the *whole inbox*, not just logging, so reads now degrade gracefully and the app shows a "Setup needed" warning.
   - **Security:** Row Level Security was off, so the public browser key could read customer names and phone numbers. It's on now for every table.
3. **"Stated temperatures" wasn't possible as written.** Opus 5.5 rejects a temperature setting, and the current Anthropic SDK has dropped the parameter. We state the choice above instead of claiming a temperature we can't set.

4. **The cost measurement found a safety bug.** "I received a damaged product" was classified as a return and got a draft, but Dhaga's escalation SOP sends damage to Tier 2. We added a `DAMAGED_OR_WRONG_ITEM` intent with a Tier 2 rule; it now scores 10/10 in the eval.

**Known gaps:**
- **Order dates:** many in-transit orders in the synthetic data are months past their expected date, so drafts mention very long delays (set `CX_TODAY` for demos).
- **Placeholder policies:** the policy texts are placeholders until the real PDFs are uploaded to the `Dhaga` storage bucket.
