How to use this guide

Read Part A once so everyone agrees on what we are building. Use Part B when you need to know where something lives. Work through Part C phase by phase. Each phase ends with a "done when" check. Don't start the next phase until that check passes.

Throughout the guide, each step is labelled by who does it:

Code deterministic Python: lookups, arithmetic, rules.   Model a call to Claude, for language and judgement.   Human an agent or manager decides.

A clickable mockup of the web app goes with this guide. Its screens are described in section 8.

Decisions to confirm before coding

The guide assumes the defaults below. Each one is cheap to change now and expensive to change later.

  1. Supabase schema. The guide uses the 10-table, UUID-keyed schema from the shared chat. The chat's last message asked for a corrected CREATE TABLE script and has no reply, so the live database may differ. Default: export the live schema in Phase 0 and fix this guide where it differs.
  2. Frontend framework. The repo currently deploys a Streamlit placeholder. Default: replace it with React + Vite, as the chat recommends, served by FastAPI from one Docker container so the Hugging Face deploy keeps working.
  3. LangChain. The chat planned LangChain for orchestration. Our flow is a fixed sequence of three model calls with code in between, which plain Python handles well. Default: call Claude through the official anthropic SDK with Pydantic schemas. Add LangChain only if the course requires it.
  4. Returns data source. The Returns backend reads local demo CSVs (SKU4421 and so on). Supabase holds a different dataset (100 products, 2,500 orders, 563 returns). Default: add a Supabase loader so one database feeds both modules, and keep the CSVs for tests.
  5. Models. Default: Claude Haiku 4.5 (claude-haiku-4-5) to classify and check, and Claude Opus 5.5 (claude-opus-5-5) to write replies. See 7.6.

Part A · Product

1. Product requirements (PRD)

1.1 Product in one sentence

Dhaga Workbench is an internal web app that helps two Dhaga teams with repetitive work. The CX team gets a draft reply for each support ticket, built from real order data. The category team learns why products are being returned.

1.2 The problems, in the client's words

Arpita · Head of CX

Support is slow and repetitive

"Fifty-eight percent of tickets are some version of where is my order." 34 agents handle about 9,000 tickets a week on Freshdesk and WhatsApp. They copy and paste the same four replies, and the first response takes 9 hours on average.

Neha · Category Head

Nobody knows why products come back

"Returns are thirty-one percent overall. When I read the Other box by hand, most of it is about fit, but I can only read a few hundred at a time." 44% of return reasons are recorded as "Other".

From those figures: 9,000 × 58% ≈ 5,220 order-status tickets a week. That is our calculation from the brief, not a number Dhaga gave us.

There is no real authentication in the MVP. A demo login and a workspace switcher stand in for it.

1.5 In scope and out of scope

In scope

  • CX: ticket inbox, intent classification, order lookup, policy-based draft reply, automatic check, human approval, escalation
  • Returns: data cleaning, return rates, flagged segments, AI classification of "Other" comments
  • One web app with both modules, a demo login and a visible failure state
  • Logging every AI call with cost and time

Out of scope

  • Sending real replies to Freshdesk or WhatsApp
  • Real login and role permissions
  • Reviews, product copy and the analytics assistant
  • Vector search and embeddings: the policy documents are short enough to send whole
  • Production scaling

1.7 Rules every feature must follow

These come from the course brief.

  • Code and model line. Every step is either code or a model call, and we can say why. Models handle language and judgement. Code handles lookup, arithmetic and comparison. A model never decides a delivery date or whether a refund is allowed.
  • Structured output. Every model call returns JSON that is checked against a schema. We never parse free text.
  • Two models. A fast, cheap model and a stronger one, with a stated reason for each.
  • Stated settings. Classification and checking run at temperature 0. Customer-facing writing uses different settings, and we write down what we chose (see 7.6).
  • Visible failure. When the system can't answer, the screen says so and hands the ticket to a person. It never guesses.
  • Human in the loop. Nothing reaches a customer without an agent's approval.

1.8 Assumptions and risks

Assumption or riskWhat would prove it wrong, and what we do
Most order-status tickets can be answered from order data aloneDrafts are often rejected for missing facts. Check which facts were missing and add them to the order lookup.
The synthetic data behaves like Dhaga's real dataWe can't fully test this. Say so in the presentation and show the data contract.
The model invents a date or a promiseThe automatic check compares every date and order number in the draft with the facts. Failures go to a human.
The model service is down or rate-limitedA keyword classifier and template replies take over, and the screen shows that fallback mode is on.

2. The two modules

2.1 Returns Insights (backend built, stage 1)

This turns raw return records into return rates and a short list of products, sizes and colours worth investigating. Stage 1 uses rules only. It cleans the data, rejects bad rows with a reason, maps sizes, colours and dropdown reasons to standard values, and flags segments whose return rate is at least 1.5× the shop average. Returns marked "Other" that have a comment are tagged needs_llm.

Stage 2 adds a model that reads those comments ("shoulders pe bahut tight hai") and assigns a category such as FIT / TOO_TIGHT / SHOULDERS. The full write-up is in the backend guide, also in this repo at docs/backend-guide.html.

2.2 CX Copilot (to build)

This helps an agent answer a support ticket in seconds instead of minutes. For each ticket it:

  1. works out what the customer wants Model
  2. finds their order and works out the facts, such as status, courier and how many days late Code
  3. applies business rules such as "RTO orders go to Tier 2" Code
  4. picks the right policy document Code
  5. writes a reply in the customer's language Model
  6. checks the reply against the facts Code Model
  7. shows everything to the agent to approve, edit or reject Human

The key principle from the chat: data answers "what is true about this order", documents answer "what does Dhaga's policy say", and the model only turns those into a reply.

4.3 Returns data flow

Stage 1 is already built: ingest → validate → normalize → join catalogue → aggregate → flag segments. Phase 5 only changes where data comes from. A supabase_loader reads two database views (see 5.3) and renames columns into the shape the existing pipeline expects. Nothing after ingestion changes. Stage 2 runs on the rows tagged needs_llm, calls Haiku 4.5 once per comment, and writes ai_category, ai_subcategory and ai_confidence back to returns.

5.3 Two database views that keep the code simple

Joins are easier to write once in SQL than in every Python function. Create these in the Supabase SQL editor:

-- One row per ticket with everything the Copilot needs
create view v_ticket_context as
select t.ticket_id, t.ticket_number, t.channel, t.message, t.status, t.created_at,
       c.customer_id, c.name as customer_name, c.city,
       o.order_id, o.order_number, o.order_status, o.payment_mode, o.courier,
       o.tracking_number, o.expected_delivery, o.delivered_at, o.total_amount
from support_tickets t
join customers c on c.customer_id = t.customer_id
left join orders o on o.order_id = t.order_id;

-- Returns in the shape the existing pipeline expects
create view v_returns_enriched as
select r.return_id, o.order_id, r.customer_id, p.product_id, p.sku,
       p.product_name, p.category, oi.size, oi.colour,
       r.original_reason as return_reason, r.customer_comment as return_comment,
       r.created_at::date as return_date, r.ai_category, r.final_category
from returns r
join order_items oi on oi.order_item_id = r.order_item_id
join orders o on o.order_id = oi.order_id
join products p on p.product_id = oi.product_id;

One subtle change: Supabase stores one row per order item, so the Returns pipeline will count items sold rather than orders. That is the right base for a return rate. Note it in the build note.

7. CX backend: detailed implementation plan

7.1 Module layout

backend/modules/cx/

Each file does one job and is short enough to read in one sitting. router.py holds no logic. Only repository.py talks to the database. Only the three model files call Claude, and they do it through shared/llm.py.

7.3 The workflow, step by step

#StepWhoDetail
1Load ticketCodeRead v_ticket_context by ticket_id
2ClassifyHaiku 4.5Message → TicketClassification: intent, confidence, order number if mentioned, language
3Find orderCodeTry the ticket's linked order, then the extracted number, then the customer's latest open order. The order must belong to this customer.
4Compute factsCodedays_late = today − expected_delivery when not delivered, plus is_cancellable, days_since_delivery and similar. All arithmetic happens here.
5Apply rulesCodeDecide whether to draft or send to a human (7.5)
6Pick policyCodeIntent → document text, from memory
7DraftOpus 5.5Facts + policy + message → DraftReply. The prompt says to use only the given facts and to reply in the customer's language.
8Check (code)CodeEvery date, order number and rupee amount in the reply must appear in the facts. An unknown value fails the check.
9Check (model)Haiku 4.5Does the reply answer the question, follow the policy and sound polite? Returns DraftCheck.
10Retry onceCodeIf either check fails, redraft once with the issues listed. If it fails again, the result is NEEDS_HUMAN.
11LogCodeInsert into ai_interactions: models, prompt versions, output, tokens, time. Set the ticket to DRAFTED.
12DecideAgentApprove, edit or reject. Save human_action and the final reply. Set the ticket to RESOLVED or ESCALATED.

This uses two of the course's patterns, each for a real reason. Routing: different intents need different facts and policies (steps 2–6). Evaluator–optimizer: a draft that fails the check is regenerated once (steps 8–10).

7.4 Schemas (what each step returns)

class TicketClassification(BaseModel):
    intent: Literal["WISMO", "DELIVERED_NOT_RECEIVED", "CANCEL_ORDER",
                    "RETURN_REFUND", "COD_PAYMENT", "OTHER"]
    confidence: float = Field(ge=0, le=1)
    order_number: str | None        # e.g. "DHC100560" if the customer wrote it
    language: Literal["english", "hinglish", "hindi", "other"]

class OrderFacts(BaseModel):         # built by code, never by a model
    order_number: str
    status: str
    courier: str | None
    tracking_number: str | None
    expected_delivery: date | None
    delivered_at: datetime | None
    days_late: int | None
    is_cancellable: bool
    payment_mode: str
    items: list[str]                 # "Green Embroidered Straight Kurta (M)"

class DraftReply(BaseModel):
    reply: str
    facts_used: list[str]            # which facts the reply relies on

class DraftCheck(BaseModel):
    passed: bool
    issues: list[str]

class CopilotResult(BaseModel):      # what the API returns to the frontend
    ticket_id: UUID
    status: Literal["DRAFTED", "NEEDS_HUMAN", "NEEDS_INFO"]
    classification: TicketClassification
    facts: OrderFacts | None
    policy_used: str | None
    draft: str | None
    check: DraftCheck | None
    human_reason: str | None         # shown on the failure card
    interaction_id: UUID
    fallback_mode: bool
    cost_usd: float
    latency_ms: int

classify  ~800 in / 150 out on Haiku   ≈ $0.0016
draft     ~2,500 in / ~550 out (incl. thinking) on Opus ≈ $0.021
check     ~1,500 in / 150 out on Haiku ≈ $0.0023
per ticket ≈ $0.025  ·  5,220 order-status tickets a week ≈ $130 a week (estimate)

Prompt caching on the policy text can cut the drafting input cost a lot, because the same policy is sent with every ticket of the same intent.

SDK. Call Claude with the official anthropic Python package and its client.messages.parse() helper. It checks the reply against our Pydantic schema, so we never parse text by hand. The SDK already retries rate limits and server errors (2 retries by default). After that, fallback.py takes over.

7.7 When things go wrong

  • Model unavailable or quota used up: the keyword classifier plus four template replies, one per main intent. These are the "same four replies" agents already use. The result has fallback_mode: true, and the screen shows a banner.
  • Schema check fails: retry once, then return NEEDS_HUMAN with "AI response could not be validated".
  • Database error: HTTP 503 with a plain message. The frontend shows a retry button.
  • Every error response uses one shape: {"error": {"code": "ORDER_NOT_FOUND", "message": "…"}}.

7.8 Tests

  • Unit: order_facts (days late, cancellable), rules (each row of 7.5), the code check in checker (a reply with an invented date fails), and fallback keywords.
  • Workflow: run copilot.py with a fake repository and a fake model client, so tests are free and repeatable.
  • Eval (Phase 7): 50 labelled tickets, run against the real model. Report intent accuracy, check pass rate and cost.

10.3 Coding rules

  1. Routers are thin. Parse the request, call one service function, return a schema.
  2. One file talks to the database per module (repository.py). Everything else gets plain data.
  3. Modules never import each other. Shared code goes in shared/.
  4. Every model output has a Pydantic schema. No string parsing.
  5. Prompts live in files with a version (draft_v1.md), and the version is logged with every call.
  6. No arithmetic or dates in prompts. Code computes them and the model only reads them.
  7. Settings and thresholds come from settings.py, never hard-coded.
  8. Small commits, one phase per branch, with tests passing before merge.
  9. Secrets only in .env. Never commit it and never send it to the browser.

11. Future plan: separate microservices

Split only when there is a reason: separate teams, different release speeds, or one module needing to scale on its own. The MVP doesn't need it. Because of the rules in section 10, the split is mostly moving folders.

Steps

  1. Check boundaries. Confirm that modules/cx and modules/returns import nothing from each other. A simple test can enforce this.
  2. Extract shared/ into a small installable package, dhaga-common, that both services depend on.
  3. Create two apps. Each service gets its own main.py, Dockerfile, settings and health check. Each mounts only its own router.
  4. Add a gateway. A reverse proxy such as Caddy or Nginx routes /api/returns/* and /api/cx/*. The frontend keeps the same URLs, so it doesn't change.
  5. Split data ownership. Each service writes only its own tables: CX writes support_tickets status and its ai_interactions rows; Returns writes the returns.ai_* columns. Shared master tables (customers, orders, products) are read-only for both, through views.
  6. Talk over HTTP, not the database. When CX needs a refund status, it calls a Returns endpoint and doesn't read the returns table directly.
  7. Deploy separately. Use separate CI jobs and environment files, and give each service its own logs and cost tracking (filter ai_interactions by workflow).

Watch out: two services sharing one database is fine for this project, but neither service may change a table the other owns. Write the owner of each table into db/schema.sql as a comment.
